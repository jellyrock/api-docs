ApiClient. ApiClient

ApiClient provides a centralized, stateful wrapper around the Jellyfin API. It automatically injects image parameters and version-specific fields for consistent, bulletproof item fetching across all Jellyfin server versions (10.7.0+).

The singleton pattern ensures one instance is shared across the entire app.

BuildAuthenticateWithQuickConnectRequest(secret) → {dynamic}

Build a request AA to exchange an APPROVED Quick Connect secret for an auth token, for use with fetchAsync() / fetchRes().

The body's field name changed at 10.8.0 — a FINER boundary than the V1/V2 apiVersion split, so it reads the server version directly rather than m.getApiVersion(): 10.7.x: { "Token": secret } (QuickConnectDto.Token, required) 10.8.0+: { "Secret": secret } (QuickConnectDto.Secret, required) Confirmed against every published spec from 10.7.0 to 10.11.8 — the rename lands at exactly 10.8.0, with no version carrying both names.

DON'T BRANCH ON THE ERROR CODE HERE. The spec declares only 400 ("Missing token") plus 503 from 10.11.0, but a live 10.11.11 answered 404 for a secret it had not seen approved — an undeclared code. So a non-ok response means "this secret cannot be exchanged" and nothing finer; quickConnectExchangeFailure (source/utils/quickConnect.bs) owns the one distinction worth making.

BuildConnectQuickConnectRequest(secret) → {dynamic}

Build a request AA to poll whether a Quick Connect secret has been approved, for use with fetchAsync() / fetchRes(). Responds 200 with the same QuickConnectResult shape Initiate returned, its Authenticated flag now true once someone approved the code.

An UNKNOWN or EXPIRED secret answers 404 ("Unknown quick connect secret"), declared by EVERY published spec from 10.7.0 to 10.11.8 and corroborated by a live 10.11.11. That is the only signal separating "not approved yet" from "this code is dead", and it is invisible to a caller that only parses the body — which is why this endpoint has to go through the pool (res.statusCode) rather than a sync JSON helper.

BuildDeleteSubtitleRequest(itemId, stream) → {dynamic}

Build a request AA to delete an EXTERNAL subtitle file from an item, for use with fetchRes().

TAKES THE STREAM, NOT AN INDEX, AND THAT IS THE POINT. The server deletes MediaStream.Path unconditionally, and for an EMBEDDED stream that path is the media container — so aiming this at the wrong stream destroys the user's movie, not a subtitle. This used to accept a bare integer and warn the caller in prose to check IsExternal first. Prose is not a guard: the subtitle panel's list was ALSO external-only at the time, so the safety rested on two separate places staying in agreement, and the moment that list grew to include embedded streams (so it could describe the item honestly) the only thing standing between a mis-wired row and a deleted container was a comment. Requiring the stream means the check happens here, once, and cannot be forgotten by a future caller.

A non-external stream returns INVALID rather than raising: callers already treat an invalid request as "cannot do this" (validatedReq does the same when no server URL is set), so refusing degrades into an inert button instead of a crash.

The one hazard left with the caller: Index must come from a FRESH item fetch. A download inserts a subtitle at index 0 and renumbers every other stream, so a stale index deletes the wrong file — or errors (observed as HTTP 400) if it now points past the end.

Unlike download, delete is SYNCHRONOUS end-to-end — the controller awaits RefreshMetadata, so the next GET /Items/{id} already reflects the new stream list (verified: correct at t+0s).

external subtitle, has no index, or the server URL is not set

BuildDownloadRemoteSubtitleRequest(itemId, subtitleId) → {dynamic}

Build a request AA to have the SERVER download a remote subtitle onto the item, for use with fetchRes() (not SubmitSideEffect — see below).

The response carries NO success information: the controller wraps the download in try/catch, logs any failure, and returns 204 either way, then queues the metadata refresh ASYNCHRONOUSLY (QueueRefresh). A missing provider, absent credentials, and an exhausted daily quota all yield the same 204 as a success. The ONLY honest completion signal is re-fetching the item and diffing its subtitle MediaStreams — see newSubtitleStreams().

BuildGetLibraryOptionsInfoRequest() → {dynamic}

Build a request AA for the server's library options, for use with fetchRes() or fetchJson(). Returns a LibraryOptionsResultDto.

Used to learn which metadata PLUGINS the server has installed — SubtitleFetchers lists every installed subtitle provider by name — so a feature that needs one can be hidden rather than offered and then fail empty. Read by source/utils/serverCapabilities.bs.

Unchanged from 10.7.0 through 12.0, and authorized for ANY signed-in user (Policies.FirstTimeSetupOrDefault), so it needs no V1/V2 branch and no admin. libraryContentType is deliberately omitted: the server then reports plugins for Series, Season, Episode and Movie — exactly the types subtitle search supports.

BuildInitiateQuickConnectRequest() → {dynamic}

Build a request AA to start a Quick Connect request, for use with fetchAsync() / fetchRes(). The response carries the Secret we poll with and the Code the user types on their other device.

The HTTP METHOD moved at the same boundary as the apiVersion split: apiVersion 1 (10.7.0 - 10.8.13): GET (no POST route exists) apiVersion 2 (10.9.0+): POST (no GET route exists) Confirmed against every published spec from 10.7.0 to 10.11.8: each version declares exactly one of the two verbs, and the swap is at exactly 10.9.0.

Sending the wrong method to a modern server yields 401 ("Quick connect is not active on this server"), which reads as a feature gate but is actually a route mismatch — so the dispatch is load-bearing, not cosmetic. That collision is also why quickConnectInitiateFailure treats 401 as "disabled": it is the same code either way, and a route mismatch is our bug, not something to tell a user.

BuildSearchRemoteSubtitlesRequest(itemId, language, isPerfectMatchopt) → {dynamic}

Build a request AA to search a server's configured subtitle providers, for use with fetchRes() or fetchJson(). Returns an array of RemoteSubtitleInfo.

language is passed straight through to the server, which resolves it via LocalizationManager.FindLanguageInfo() — that matches case-insensitively on DisplayName, Name, TwoLetterISOLanguageName, OR either ISO 639-2 variant (/T and /B both live in ThreeLetterISOLanguageNames). So "fra", "fre", "fr" and "French" are all accepted. Prefer the TWO-letter form from /Localization/Cultures: it is what reaches the provider, and it preserves regional variants that the 3-letter form collapses (zh-tw / zh-cn / zh-hk all share "zho"; es-419 shares "spa" with Castilian).

a true value returns ONLY results whose IsHashMatch is set, which is frequently an empty list.
